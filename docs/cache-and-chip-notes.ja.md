# GSU のキャッシュと、GSU-1 / MARIO chip（MC1）の違い

実機で測ったことと、ドキュメントに書かれていることを分けてまとめる。
「推測」と書いたもの以外は、実測またはドキュメントの記述である。

## 1. 対象

| | GSU-1 | MARIO chip（MC1） |
|---|---|---|
| カート | 基板 1CA6B-01 | 日本版スターフォース、基板 1C0N |
| VCR（$303B） | 04 | 01 |
| クロック | カート上の発振器 | 外部から SYSTEM CLK を供給 |
| /ROMSEL（ピン 49） | 未接続（開放） | 外部で H に固定 |
| ホスト | Raspberry Pi Pico（RP2040）が S-CPU の代わりにレジスタ窓 $3000〜$32FF を操作 | 同左 |

VCR は、fullsnes では 1 が MC1、4 が GSU-2 とされ、GSU-1 の値は載っていない。
GSU-1 のカートが 04 を返したので、04 は GSU-1 として矛盾しない。

## 2. ドキュメント上のキャッシュの仕組み

出典は SnesLab の Super FX のページ（末尾）。

- 512 バイトで、16 バイトのブロックが 32 個ある。各ブロックに「使用中」のフラグがある。
- SNES 側からは $3100〜$32FF に見える。コードの開始位置は `$3100 + (CBR & 0x1FF)`。
- CBR（$303E/$303F）は読み出し専用。下位 4 ビットは使われない。
- ホストがキャッシュにコードを書く場合は、16 バイトのブロック単位で書く。ブロックの最後のバイト（$xxxF）を書くと、そのブロックが「使用中」になる。
- その場合、R15 は $0000〜$01FF の範囲でなければならない。
- 専用の有効化フラグはない。キャッシュは常に GSU が使う。GSU が止まっていれば、ホストも読み書きできる。
- キャッシュに入っているブロックは、1 命令 1 サイクルで実行できる。キャッシュに入っていないコードは、ROM/RAM から読まれて実行される（ROM は 1 命令に 3 サイクル以上）。
- 自動キャッシュは、CACHE 命令または LJMP で始まる。このとき、フラグが全部消えて、CBR = PC & 0xFFF0 になる。以降、実行した命令がキャッシュに書き込まれる。
- SFR に GO=0 を書くと、フラグと CBR が消える。STOP や GSU の起動では、キャッシュの内容は保たれる。

## 3. ファームが設定している値

| 項目 | 値 | 備考 |
|---|---|---|
| SFR | 0000 を書く（GO=0） | キャッシュのフラグを消し、CBR を 0 にする。キャッシュを書く前に 1 回だけ行う |
| キャッシュの書き込み | $3100〜、16 バイト単位 | 最後のバイトで「使用中」になる |
| PBR | 0 | プログラムバンク |
| SCMR | 0x18（RAN と RON） | GSU が RAM と ROM のバスを持つ |
| CFGR | 0x80 | bit7 = IRQ マスク。bit5（MS0、乗算の高速モード）は 0 |
| CLSR | 00（10.7 MHz）または 01（21.4 MHz） | 書き込み専用で、読み戻せない |

CFGR の bit5 は、21 MHz モードでは 0 でなければならない（fullsnes）。
一時期、IRQ マスクのつもりで 0x20 を書いていたが、それは bit5 であり、0x80 に直した。

## 4. 実測

### 4.1 GSU-1

- ホストが書いた 32 バイト（2 ブロック）のプログラムが、最後まで正しく動いた。
- ホストが書いた 80 バイト（5 ブロック）のプログラムも動いた。
- キャッシュの書き込み→読み戻し（$3100〜$32FF の 512 バイト）が一致した。
- 21.4 MHz（CLSR=01）で動いた。
- STOP の後、SFR は 0000 だった（IRQ フラグが見えない）。
- 診断 [6]（ブロックごとのテスト）: ブロック 1 だけ（0x10 開始）、ブロック 1 の先頭の STOP と途中からの再開、ブロック 0 から 1 へのフォールスルー、ブロック 1 への前方向の分岐、ブロック 0 → 1 → 0 の分岐、ブロック 1 の中の分岐、ブロック 31 だけ（0x1F0 開始）が、すべて期待どおりに動いた。
  （診断の最初の版には、期待値の誤りが 3 つあった: STOP の位置からの R15 の値と、IBT の符号拡張（`IBT R3,#99` は R3=FF99）。これらは直してある。）
- 診断 [7]: ブロック 1 で終わる実行の直後に、ブロック 0 のプログラムを開始しても成功した（ステップ 2、3 とも PASS）。GSU-1 は、直前に実行したブロックに関係なく、書いた全ブロックが使える。
- クロック（診断 [5]）: 比は 2.00（24,442 µs と 12,219 µs）。MC1 と同じ。

### 4.2 MC1

**基本動作（診断 [1]〜[5]）はすべて PASS** した。

- レジスタの書き込み/読み戻し、ラッチ動作、キャッシュの読み戻し（512 バイト一致）。
- ブロック 0 から開始して、STOP と再開（R15 の書き戻し）が動く。
- クロック（診断 [5]）: 65,535 回のループの所要時間が、CLSR=00 で 24,426 µs、CLSR=01 で 12,211 µs。比は 2.00。
  命令の速度は約 8.0 MHz と約 16.1 MHz。CLSR=01 で速度が 2 倍になる。
- STOP の後の SFR は 8000（IRQ フラグが立ったまま）。GSU-1 は 0000。

**診断 [6]（ブロックごとのテスト）**

プログラムをホストから書いて、GSU を起動し、1 回目の STOP の位置と R1、R2 を確認した。

| テスト | 結果 |
|---|---|
| ブロック 1 だけ、0x10 から開始 | 失敗。最初の命令が `00`（STOP）として実行された（R15=0012、期待は 0014） |
| ブロック 1 だけ、先頭が NOP、0x10 から開始 | 失敗。同じく `00` で STOP（ROM の 0x10 が `00` なので、ROM の内容と一致する） |
| ブロック 1 の先頭に STOP を置き、0x12 から再開 | PASS。再開後は、こちらのコード（`A1 5A`）が実行された |
| ブロック 0 とブロック 1 を書き、0 から開始 | 失敗。最初の命令が `00` で STOP（R15=0002） |
| ブロック 0 とブロック 1 を書き、0x0A から開始 | 失敗。IBT が実行されなかった |
| ブロック 0 だけ、0x02 から開始 | PASS |
| ブロック 31 だけ、0x1F0 から開始 | 失敗。R15=0217 まで暴走し、CBR=0008 になった |

**デモプログラムの経過（トレース）**

32 バイトのデモ（2 ブロック）を実行した。

- 最初の 3 回の STOP は正常だった（R15 が 0004、000D、0012）。最初の文字は、+1 されて正しく返った。
- 4 回目の STOP が 0x1F になった。0x1D に STOP があるはずがない位置である。
- そこで止めてキャッシュを読み出すと、ブロック 0 は書いたとおり（`A1 02 00 01 3E 71 09 F8 ...`）で、ブロック 1 以降は
  `00 80 3B C2 30 A9 1F 7C 8D F4 1F A2 BA 00 80 01 ...` だった。
  `C2 30 A9` は 65816 の命令に見えるので、ROM の内容だと思われる。0x1D（`00`）が STOP になった位置と一致する。
- ブロック 1 以降が ROM の内容に置き換わっている。ブロックが「使用中」でなかったために ROM から読まれ、キャッシュに書き込まれた、と考えると説明がつく（推測）。

**クロック（21 MHz）**

- 短い診断（[4]、[5]）は、21 MHz でも PASS した。
- 長いプログラムを動かすと、21 MHz では暴走した（STOP に到達せず、SFR=0020 のまま）。10.7 MHz では動いた。
- MC1 の定格は 10.7 MHz とされている。21 MHz の不安定さの原因は不明。外部クロックの品質も疑える。

**ROM/RAM から自動で読み込むコード**

キャッシュの内容を使わず、LJMP でカート RAM（バンク $70）に飛んで、RAM から命令を読む場合は、10.7 MHz で正しく動いた。
自動キャッシュ（LJMP の後に、実行した命令がキャッシュに入る仕組み）は、MC1 でも動く。

**再開のたびにキャッシュを書き直す方法（旧ビルドの `RELOAD_CACHE_ON_RESUME=1`。現在は削除）**

10.7 MHz で、32 バイトのデモを試した。

- `H` を打つと `I` が返った。ここまでは正常。
- その後、0x12 の `BRA $00` でブロック 0 に戻るはずが、0 番地の STOP（`00`）が実行された（R15=0002）。
- そのときのキャッシュの先頭は `00 00 00 01 ...` で、書いたはずの `A1 02` が `00 00` に変わっていた。ROM の 0 番地付近の内容に見える。
- 書き直しを毎回行うので、その後は正常な流れに戻る。ただし余分な文字が 1 つ出た。
- ブロック 0 の中で戻る分岐（状態確認のループ）は、問題なく動いていた。

ブロック 1 から、ブロック 0 へ分岐したときに、キャッシュではなく ROM から読まれた可能性がある（推測）。
診断 [6] に、ブロックをまたぐ分岐のテストを追加した。

**ブロックをまたぐ分岐のテスト（診断 [6] の追加分、10.7 MHz）**

| テスト | 結果 |
|---|---|
| ブロック 0 から 1 へ分岐（前方向） | 失敗。最初の命令が `00` で STOP（R15=0002） |
| ブロック 0 → 1 → 0 | 最初の命令（IBT R1）は成功（R1=0001）。ブロック 1 への分岐先で `00` の STOP（R15=0012、R2=0） |
| ブロック 1 の中の分岐 | 失敗。最初の命令が `00` で STOP（R15=0002） |

## 4.3 仮説: ホストが書いたコードは「最後に実行したブロック」でしか使われない（MC1）

診断 [6] の全テストの結果は、次の仮説で説明できる。診断 [7] の 1 回の実測で、予測どおりの結果になった（支持された。他に例外がないことまでは確認していない）。

> MC1 では、ホストが書いたキャッシュのコードは、直前の実行で最後にいたブロックの中でだけ使われる。
> 別のブロックに入る（開始、分岐、順に実行して境界を越える）と、ROM（PBR:PC）の内容が読まれ、キャッシュに書き込まれる。

「直前の実行が終わったブロック」と「次の実行が使うブロック」の関係:

| 直前の実行が終わった場所 | 次の開始位置 | 結果 |
|---|---|---|
| ブロック 0 | ブロック 0（0 または 0x02） | 成功 |
| ブロック 1 | ブロック 1（0x12 での再開） | 成功 |
| ブロック 0 | ブロック 1（0x10） | 失敗（ROM の `00`） |
| ブロック 1 | ブロック 0（0 または 0x0A） | 失敗 |
| ブロック 0 | ブロック 31（0x1F0） | 失敗（ROM のコードを実行して暴走） |
| 実行中に、ブロックの境界をまたぐ分岐やフォールスルー | | 分岐先が ROM の内容になる |

この仮説で、次のことも説明できる。

- デモが、ブロック 1（0x10）に入った所で止まったこと。ROM の 0x10 が偶然 `00`（STOP）だったため、STOP に見えた。
- 再開しても、ブロック 1 全体が ROM の内容になっていたこと（順に実行して、バイトごとに ROM から取り込んだ）。
- 毎回書き直しても、ブロック 1 から 0 へ戻る分岐だけが失敗したこと。先頭の 2 バイトだけが `00 00` に書き換わった（ROM の 0 番地付近）。

SnesLab の「各ブロックに使用中のフラグがある」とは違い、MC1 は実質ブロック 1 つ分の動作に見える。

**診断 [7] の結果（10.7 MHz）**

| ステップ | 内容 | 結果 |
|---|---|---|
| 1 | ブロック 1 で終わる実行（準備） | 完了（R15=0016） |
| 2 | その直後に、ブロック 0 の `IBT R1,#5A; STOP` を 0 から開始 | 失敗（R15=0002、最初の命令が ROM の `00`） |
| 3 | 直後に同じプログラムをもう一度開始 | 成功（R1=005A、R15=0004） |

同じプログラム、同じ開始位置で、直前の実行が終わったブロックだけが違う。

## 4.4 GSU-1 と MC1 の比較（診断 [6]、[7]、10.7 MHz、同じビルドで 2 回実行して再現）

| テスト | GSU-1 | MC1 |
|---|---|---|
| ブロック 1 だけ（0x10 開始） | PASS | FAIL（R15=0012、ROM の `00` で STOP） |
| ブロック 1 の先頭に STOP し、0x12 から再開 | PASS | PASS |
| ブロック 0 からブロック 1 へフォールスルー | PASS | FAIL |
| 0 から開始し、ブロック 1 へ命令が続く | PASS | FAIL（R15=0002） |
| ブロック 0 の中（0x02 開始） | PASS | PASS |
| 先頭が NOP（0x10 開始） | PASS | FAIL（R15=0012） |
| ブロック 0 → 1（前方向の分岐） | PASS | FAIL（R15=0002） |
| ブロック 0 → 1 → 0 | PASS | FAIL（R1=0001 まで。0x10 で STOP） |
| ブロック 1 の中の分岐 | PASS | FAIL（R15=0002） |
| ブロック 31 だけ（0x1F0 開始） | PASS | FAIL（R15=0217 まで暴走） |
| [7] ブロック 1 で終わった直後にブロック 0 を開始 | PASS | FAIL（R15=0002） |
| [7] 直後にもう一度 | PASS | PASS |
| [7] の判定 | 書いた全ブロックが使える | 最後に実行したブロックだけ |
| STOP 後の SFR（IRQ フラグ） | 0000 | 8000 |
| クロックの比（CLSR 00 / 01） | 2.00 | 2.00 |

### 4.5 STB の直後の STOP（実測）

テストプログラム（`$0200` にロード、各 1 万回）で確認した。GSU-1 は 4 パターンとも完走（`AaBbCcDdEND`）。MC1 は `STB (R3); STOP` で止まり（`A` の後 `TIMEOUT`、SFR=0022 = GO が立ったまま）、fullsnes の報告どおり。STW 直後（B）と NOP 1 個を挟んだ場合（C）も止まり、NOP 4 個（D）なら完走する。NOP 2 個（G）、3 個（H）も完走する（各 2 回確認）ので、最小は 2 命令。ローダーと stage 1 は STB と STOP の間に 5 命令あるので安全。

## 4.6 乗算の速度（CFGR.MS0）

CFGR のビット 5（MS0）は乗算の高速モードで、21 MHz では 0 のままにする。命令ごとの小さなプログラムで測った（`CACHE`、`LOOP` で 32 個の同じ命令を 56470 回、`l` して `t` で時間を見る）。サイクル数は NOP ループの時間から基準を取って計算した（クロックは GSU-1A のカートで 10.708 MHz と 21.415 MHz）。

**プログラムは `CACHE`（`$02`）で始める。** ローダーの最後の `LJMP` は、ジャンプ先ではなくジャンプ元（`$004E` 付近）から CBR を決めるので、CBR は `$0040` になり、窓は `$0040`〜`$023F` になる。`$0200` のプログラムは、先頭の 64 バイトだけがキャッシュに乗り、あとは ROM/RAM の速さ（1 バイト約 3 サイクル）になる。`CACHE` を先頭に置くと窓が `$0200`〜`$03FF`（512 バイト）になる。NOP を N 個並べたループの 1 命令あたりのサイクル数は、`CACHE` なしで 1.00 / 1.55 / 2.26 / 2.62（N = 32 / 64 / 128 / 256、GSU-1A と MC1 で同じ）、`CACHE` ありはどれも 1.00。

キャッシュ上の乗算（GSU-1A、VCR=04）。1 命令あたりのサイクル数：

| クロック | MS0 | MULT | UMULT（ALT1 込み） | FMULT | LMULT（ALT1 込み） |
|---|---|---|---|---|---|
| 10.7 MHz | 0 | 1 | 3 | 8 | 9 |
| 10.7 MHz | 1 | 1 | 2 | 4 | 5 |
| 21.4 MHz | 0 | 1 | 3 | 8 | 9 |

時間にすると：

| クロック、MS0 | MULT | UMULT | FMULT | LMULT |
|---|---|---|---|---|
| 10.7 MHz、0 | 93 ns | 280 ns | 747 ns | 840 ns |
| 10.7 MHz、1 | 93 ns | 187 ns | 374 ns | 467 ns |
| 21.4 MHz、0 | 47 ns | 140 ns | 374 ns | 420 ns |

仕様書上の値（sneslab.net の各命令ページ、キャッシュ実行）は、MULT 1 または 2、UMULT 2 または 3、FMULT 4 または 8、LMULT 5 または 9。UMULT / FMULT / LMULT の実測はこれと一致する（MS0=0 が大きいほう、MS0=1 が小さいほう）。MULT も一致する。ただし MULT を連続させると MS0=0 で 1.03 サイクル（MS0=1 は 1.00）だが、MULT を 1 個ずつ NOP で区切ると、MS0=0 で 2 サイクル、MS0=1 で 1 サイクルになる（10.7 MHz でも 21.4 MHz でも同じ）。標準速度の MULT の 2 サイクル目は、次に MULT が続くと重なる。上の表の MULT の 1 は連続実行での値。UMULT / FMULT / LMULT も連続実行で測っていて、1 個ずつの場合は未測定（`[VERIFY]`）。

- GSU-1A（10.7 MHz）では MS0=1 が効く。UMULT / FMULT / LMULT が 1、4、4 サイクル短くなる（FMULT で 747 ns → 374 ns）。MULT（8×8）は変わらない。
- キャッシュ上なら、乗算はクロックに比例する。21.4 MHz（MS0=0）はサイクル数が 10.7 MHz と同じで、時間は半分になる。FMULT は 10.7 MHz + MS0=1 と同じ 374 ns で、ほかの命令はもっと速い。21.4 MHz では MS0 を 0 にするので、GSU-1 / GSU-2 では乗算が多くても `c 1` を使う。
- 以前の測定（`CACHE` なし）は、乗算のループが窓の外（ROM/RAM の速さ）で動いていた。GSU-1A の 10.7 MHz は、MS0=0 が 3.35 / 9.27 / 11.28 / 14.29、MS0=1 が 3.25 / 6.25 / 7.24 / 10.24、21.4 MHz が 5.54 / 11.53 / 12.53 / 17.55。「21.4 MHz では乗算が 8〜15 % しか速くならない」はこの測定の結果で、乗算器の性質ではなかった。MC1 は同じ測定で 3.33 / 9.22 / 11.21 / 14.20（MS0 の 0 と 1 で同じ）で、MS0 を無視しているように見える。キャッシュ上での MC1 の乗算は測っていない（`[VERIFY]`）。
- MC1（キャッシュ上、10.7 MHz、同じ命令の連続）は MULT 1.03、UMULT 3.00、LMULT 9.00 サイクルで、MS0 の 0 と 1 で同じ。MC1 は MS0 を無視する（キャッシュ上でも確認）。FMULT は、非ゼロの被乗数（`FROM R1 ; FMULT`）なら 8.00 サイクル、FMULT の結果が次の入力になって R0 が 0 になった連続実行では 4.78 サイクルだった。MC1 では FMULT の時間がデータに依存する（GSU-1A は 0 の連続でも 8。非ゼロは未測定）。21.4 MHz は既知の暴走で測れない（`[VERIFY]`）。
- キャッシュ上の実測は、すべて仕様書のサイクル数と矛盾しない。仕様書には、データ依存、MC1 が MS0 を無視すること、下の 5.6 のハングは書かれていない。`CACHE` なしの以前の値は、先頭の 64 バイトしかキャッシュに乗らず混ざった値なので、ROM/RAM の列とは比べられない。
- GSU-2 は未測定。GSU-1 と同じとみなす。

## 5. 未解決の問題（MC1）

原因が分かっていない MC1 の問題は 3 つある。どれも、実用上は回避できている（または影響がない）ので、対応の予定はない。
調べる場合の手がかりを、項目ごとに書いておく。

### 5.1 21 MHz で暴走する

- **症状**: CLSR=01（21.4 MHz）で、ローダーを使うビルドが動かなかった。STOP に到達せず、`TIMEOUT: GSU still running, SFR=0020` が出続けた。10.7 MHz では動く。
- **分かっていること**:
  - 短い診断（[4]、[5]）は 21 MHz でも PASS し、クロックの比は 2.00 だった。CLSR は効いている。
  - デモも、21 MHz では最初の 1 文字を返した後で壊れたが、これはキャッシュの問題（5.2）と混ざっていて、クロックだけの原因とは言えない。
  - GSU-1 は 21 MHz で問題なく動く。
  - MC1 の定格は 10.7 MHz とされている。
- **分かっていない点**: 外部クロック（21.477 MHz の供給）の品質のせいか、MC1 の限界か。
- **影響と回避**: 既定の 10.7 MHz のまま使う（モニタの `c 0`）。
- **調べるなら**:
  - クロックの波形を、オシロで見る。
  - 診断 [5] のループを、長く（時間を延ばして）実行する。
  - ステージ 1 から RAM に飛んだ後のコードを、21 MHz で動かして、どこで止まるかを見る。

### 5.2 ホストが書いたキャッシュが、最後に実行したブロックでしか使われない

- **症状**: 4.2〜4.4 のとおり。別のブロックに入ると、キャッシュではなく ROM の内容が読まれる。
- **分かっていること**: 診断 [6] の全テストと、診断 [7]（2 回実行して再現）が、「最後に実行したブロックの中でだけ命中する」という仮説と一致している。GSU-1 では起きない。
- **分かっていない点**:
  - なぜそうなるのか。SnesLab は「各ブロックに使用中のフラグがある」と説明しているが、MC1 は 1 ブロック分の動作に見える。
  - 他に例外がないか。
  - ROM/RAM から自動で取り込むキャッシュ（LJMP の後）が、複数ブロックを保持できるか。
- **影響と回避**: ホストが書くキャッシュのコードは、16 バイト以内の 1 ブロックに収める。それ以外の長いコードは、RAM や ROM に置いて、LJMP で飛ぶ（2 段階ブート）。
- **調べるなら**: RAM 上の、ブロックをまたぐ小さなループを、10.7 MHz で動かして、反復あたりの時間を測る。キャッシュ速度なら複数ブロックを保持できる。毎回 ROM/RAM を読むなら遅くなるので、1 ブロックしか保持できない。

### 5.3 STOP の後の SFR が 8000（IRQ フラグが残る）

- **症状**: STOP の後、SFR の上位バイトが 80（bit 15 の IRQ）になっている。GSU-1 は 0000。
- **分かっていること**: ポーリングは SFR の下位バイトだけを読んでいる。ファームは、STOP の後に SFR の上位バイトを読んで、フラグを消している。動作には影響がない。
- **分かっていない点**: GSU-1 で 0 に見えるのは、上位バイトを読んでいないのに消えているため。チップによって、IRQ フラグの消え方（読み出しで消える範囲）が違うのかもしれない。
- **調べるなら**: 下位バイトを読んだ直後と、上位バイトを読んだ直後に、SFR を読み直して比べる。

### 5.4 CBR が 0040（解決済み）

- **症状**: `$0200` にロードして `$0200` から実行した後、モニタの `r` が `CBR=0040` を返す（GSU-1）。
- **原因**: ローダーの最後の `LJMP` がジャンプ元の番地（`$004E` 付近）から CBR を決めるので、CBR は `0040`、キャッシュ窓は `$0040`〜`$023F` になる。`$0200` のプログラムは先頭の 64 バイトだけがキャッシュに乗る。NOP ループで確認した（GSU-1A と MC1。`CACHE` なしは N = 32 / 64 / 128 / 256 で 1.00 / 1.55 / 2.26 / 2.62 サイクル、`CACHE` ありは全部 1.00）。
- **対策**: プログラムを `CACHE`（`$02`）で始める。CBR が `$0200` になり、窓が `$0200`〜`$03FF` になる。乗算の速度は 4.6。

### 5.6 乗算と他の命令を混ぜた短い列でハングする（MC1）

- **症状**: MC1 で、`MULT ; NOP` を 16 回（`mulc_I`）、`FROM R1 ; ALT1 ; LMULT` を 32 回（`mulc_H` と繰り返しを 1000 回にした `mulc_S`）の 3 つがハングした。GSU-1A では `mulc_I` が動く（H と S は GSU-1A では未実行）。
- **動くもの**: 同じ乗算の連続、`FROM R1 ; FMULT` の 32 回、`mult_check`（各種の乗算を 1 回ずつ並べた直線のコード）。
- ループの閉じ方（`LOOP` か `DEC R12 ; BNE` か）、先頭が `CACHE` か `CACHE ; NOP` か、繰り返しが 1000 回か 56470 回かは関係なく、どれもハングした（`mulc_BI`、`mulc_BS` を含む）。
- **別の観察**: NOP だけの小さなループ（`CACHE ; NOP ; FOR: ... ; BRA FOR ; NOP`）は MC1 でキャッシュから動いた。`CACHE` の直後の NOP がないと、1 周したところでハングした（報告のみ、テストファイルでは再現していない）。
- **分かっていない点**: 原因。ハングする本体はどれも乗算のあとに別の命令（NOP、FROM）が続くが、FMULT のあとの FROM ではハングしない。
- **当面**: MC1 では、乗算とほかの命令を混ぜた長いループを避ける。

### 5.5 R14 に書くと、最初の syscall のあとで古いコードが走る（MC1）

- **症状**: 146 バイトの計算プログラム（マンデルブロ風、`$0200` にロード）が、GSU-1 では正しく動くのに、MC1 では最初の syscall のあとから直前にロードしたプログラム（echo）のコードを実行した。EXIT や `BAD OP` が、そのプログラムの番地で出た。
- **回避**: 途中の値を R14 に入れず、RAM に書いておく（STW / LDW）と、MC1 でも正しく動いた（わずかに遅くなる）。確認済み。
- **分かっていない点**: R14 は ROM アドレスのポインタで、仕様書では ROM アクセスのときに使われる（R14 に書くと ROM の読み出しが始まる）。計算プログラムは ROM に触らないので、原因は不明。5.2 のキャッシュの動きと関係があるかもしれない。

### 5.7 MC1 の RAM ダンプ（v1.4.0、確認済み）

- **背景**: `$6000`〜`$7FFF` の窓は MC1 では RAM を見せない（診断 [8]）。MC1 は RAM をバンク `$70`〜`$71` にだけ置き、そのとき /ROMSEL が Low である可能性が高い（未確認）。
- **対応**: GP26 で A20、A21、A22（ピン 45〜47、まとめて 1 本）を、GP27 で /ROMSEL（ピン 49）を、GP28 で A15（ピン 40、1.4.1 から）を駆動する。ふだんは Low、High、Low（以前の固定レベルと同じ）で、`d` のときだけ GP26 を High、GP27 を Low にして、A0〜A15 のアドレス線で `$70:0000`〜`$FFFF`（64 KB）を直接読む。モニタの `b` で選ぶ（`b` が自動で MC1 はバンク `$70`、他は窓、`b 0` が窓、`b 1` がバンク `$70`）。
- **確認結果**: 配線した MC1 で、バンク `$70` に RAM が見えた（`l` のあと `$0000` にローダーの `A3 03 ...`）。MC1 は RAM をバンク `$70` に置き、/ROMSEL が Low のときに見せる。GSU-1 では `b 0` と `b 1` が同じ結果だった。RAM の容量を超えるアドレスはミラーで見えた（MC1）。GSU-2 は未実行。配線がないと、バンク `$70` では RAM が見えない。

## 6. 実用上の指針

- MC1 では、ホストがキャッシュに書くコードは、1 つのブロック（16 バイト以内）に収め、その中だけで実行する。ブロックの境界をまたぐ実行（分岐、順に進む場合）は、ROM の内容が読まれる。
- 開始するブロックが、直前の実行が終わったブロックと同じでなければならない。診断 [7] のとおり、直前がブロック 1 だと、ブロック 0 の開始は失敗する。
- 長いプログラムは、ホストが書くのではなく、RAM や ROM に置いて、LJMP で飛ぶ。命令は自動でキャッシュに取り込まれる。
- MC1 では R14 に書かない。途中の値は RAM か R12/R13 に置く（5.5）。
- MC1 のクロックは 10.7 MHz（CLSR=00）にする。
- GSU-1 では、複数ブロックのプログラムを、ホストから書いて動かせる。21 MHz も動く。
- プログラムは `CACHE`（`$02`）で始める（5.4）。
- GSU-1 / GSU-2 では `c 1`（21.4 MHz）を使う。乗算もクロックに比例して速くなる。10.7 MHz で使うときだけ、乗算が多ければ `m 1`（MS0=1）を足す。MC1 では `c 0` のままにする（4.6）。
